Annotation guide

Gerbil is a static analysis that splits each API test into API invocation steps. You are checking whether that split is right. Judge what the test code does, not how you think the tool works, and do not discuss individual tests with the other annotators.

The three kinds of item

dispatch
The call that sends an HTTP request to the application under test, such as mockMvc.perform(...), .exchange(), given()...get("/x") or restTemplate.getForEntity(...). Each dispatch starts one step. A request dispatched in-process, without a network, still counts: mockMvc.perform(...), WebTestClient bound to the application and similar test clients run the application's own request handling. Stubbing or verifying a mocked HTTP client, calling a third-party or stub server (WireMock, MockWebServer), and building a request object that is never sent are not dispatches.
builder
A call that configures a request before it is sent. It sets the request's method, path, a header/auth (any header, or credentials or a token however they are sent; one part, as the paper counts them), a parameter (query, path or form), or the body. A builder belongs to the step whose request it configures. Calls that only start or join a request chain and set none of these, such as given() or when(), are not builders and are not highlighted. A call that does set one of them but is not highlighted is a missed builder.
check
A call that can fail the test because of the HTTP response: its status, its body, or its headers. A value read from the response and asserted later still counts, with the part of the response it came from. Assertions about anything else (database rows, mock interactions, values that never came from a response) are not checks. A check belongs to the step whose response it inspects.

What to do for each test

  • Read the test method, then the setup, teardown and helper code shown under it. Highlighted calls are what Gerbil extracted; the small number is the step it put the call in.
  • Answer every line of every card on the right. All correct answers a whole card at once when nothing is wrong.
  • Look for what Gerbil missed. Click a line number (shift-click to extend), then Add missed item. Select every line of the missed call's statement, from its first line to its last, so that your selection and the other annotators' overlap.
  • Tick the box at the bottom if the test calls code that is not shown and probably sends requests or checks responses, then Mark complete.

Rules that keep us consistent

Requests that do not reach the application. A request to a mocked HTTP client, a stub server or a third-party service is not the application's: answer No on its dispatch, builder and check cards, even in a test that also calls the application. A test whose requests all go there has every card answered No.
Paths are judged on the dispatch. A builder's parts can leave out path when Gerbil could not resolve the path's value. When the dispatch says "Path: not resolved", a builder such as get(BASE_URL + id) listing only method is the same abstention: answer Correct if the rest of its parts are right, and judge the path on the dispatch card.
Judge the claim, not the token. In andExpect(status().isNotFound()) Gerbil highlights one call of the chain. You are judging "this checks the status and expects 404", not which word carries it.
One check per call that can fail the test on its own. Three andExpect(jsonPath(...)) clauses are three body checks. Add a missed check per such call, not per line.
One assertion, two cards. In andExpect(header().string("Location", url)) Gerbil can highlight both header() and string(...) as checks. They are one check: answer Yes on string(...) and No on header(), which only opens the header assertion. The same holds for cookie(). When header() or cookie() is the only card on its clause, judge it as the check.
Paths. Ignore scheme, host and port. A variable segment is written in braces and its name does not matter, so "/users/" + id is /users/{id}. Ignore the query string. If Gerbil's path is a correct prefix that stops at a variable (for example /users/), answer Partly.
Helpers run once per call. A helper called twice appears as two sets of items on the same highlighted call. Judge each set for the step it is in.

"Not resolved" is not a wrong answer

Sometimes Gerbil finds a request or a status check but cannot tell its method, path or status code, and says so. That is the tool declining to answer, so there is nothing to mark right or wrong. Instead, tell us whether the value is readable:

  • I can read it: the value is visible in the code shown (a literal, a constant, a simple concatenation). Enter it. This counts as something Gerbil missed.
  • Cannot be determined: the value only exists at run time (a URL returned by an earlier response, a random port, a value from configuration you cannot see). This counts as Gerbil correctly declining.

A value Gerbil did report is judged normally, as correct, partly correct or wrong.

Code that is not shown

You see the test method, its fixtures, and the helpers it reaches in its own class and superclasses. If the test calls other code that probably sends requests or checks responses (a client wrapper in another class, for example), tick the box at the bottom. Do not go looking for that code.

Saving

Choose the annotator id you were given (author1, author2, …) at the top; the page never asks for your name. Your answers are saved in this browser as you go. When you finish, or to move to another machine, use Export and send the file. It holds your id and your answers, with no name, date or file path. Import restores an exported file.
